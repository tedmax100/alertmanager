1. 架構全景概覽 (System Overview)

在雲原生與微服務監控體系中，Prometheus 專注於指標採集與規則評估（Scraping & Rule Evaluation），而 Alertmanager 則專職負責告警事件的後續生命週期管理。

當 Prometheus 評估出處於 firing 或 resolved 狀態的告警時，會透過 HTTP POST 推送給 Alertmanager。Alertmanager 在接收到原始告警後，承擔以下核心職責：

  1. 去重 (Deduplication)：多個 HA 節點發送的相同告警僅保留一份。
  2. 分組 (Grouping)：將屬於相同維度（如同一服務、集群）的相關告警打包為單一通知，防止告警風暴（Alert Storm）。
  3. 抑制 (Inhibition)：根據根因關係（如主機宕機 NodeDown），自動過濾衍生告警（如該主機上的 Pod 異常）。
  4. 靜音 (Silencing)：在維護窗口或已知問題期間，基於標籤規則與時間範圍阻斷通知。
  5. 路由 (Routing)：透過樹狀路由層級（Route Tree）與匹配器（Matcher），精準將告警分派至 Slack、PagerDuty、Webhook、Email 等接收端。
  6. 無中心高可用叢集 (HA Gossip Mesh)：各實例間透過 Gossip 協議互聯，同步通知狀態（nflog）與靜音資訊，杜絕單點故障（SPOF）。

2. Alertmanager 核心模組與內部實作解析

從 Alertmanager 官方 Go 源碼目錄劃分，可精確對應至以下核心子系統：

源碼目錄 核心職責與代表型別 設計架構與關鍵演算法
cmd/alertmanager/ CLI 命令列入口、旗標解析 輕量封裝，解析 --config.file、--cluster.* 旗標後呼叫 app/。
app/ 嵌入式運行時生命週期 (Runtime Lifecycle) 擁有啟動 (Start)、停止 (Stop)、熱重載 (Reload)、叢集等待 (clusterWait) 與 HTTP 伺服器掛載。
api/v2/ OpenAPI RESTful API (v2) 接收 Prometheus 推送之告警陣列、查詢/建立 Silence 規則、查詢叢集成員狀態。
provider/mem/ 純記憶體告警儲存庫 (In-memory Store) 以告警標籤指紋 (Fingerprint) 為 Key 索引，背景協程定時回收過期已解決告警。
dispatch/ 路由樹遍歷、分組狀態機 (aggrGroup) 深度優先 (DFS) 遍歷路由節點、GroupKey 計算、定時聚合調度槽位 (slot)。
notify/ 裝飾者通知流水線 (Pipeline Stages) 責任鏈模式：ClusterWaitStage → DedupStage → RetryStage → SetNotifiesStage。
nflog/ 通知歷史日誌 (Notification Log) Protobuf 結構化儲存，記錄每個 Receiver 的發送時間戳與告警指紋，去重之核心依據。
cluster/ HashiCorp Memberlist Gossip 叢集實作 節點健康探測、nflog 與 silences 的 Push-Pull 及廣播擴散。
inhibit/ 根因抑制規則引擎 (Inhibitor) 比對 Source Alert 與 Target Alert 之標籤相等性，自動過濾次級衍生異常。
silence/ 時間窗口與標籤過濾靜音引擎 支援維護窗口定時靜默、緊急告警遮蔽，透過 Gossip 廣播 Tombstone。

2.1 告警接收與儲存 (provider/mem & api/v2/)

Prometheus 透過 POST /api/v2/alerts 推送告警集合。請求由 api/v2/restapi 進行校驗，並轉換為內部模型 types.Alert。

Alertmanager 內部採用純記憶體管理告警集合（provider/mem），每條告警以標籤集合的 64 位元哈希（Fingerprint）作為索引 Key，由背景定時維護協程清除過期項目，不依賴任何外部關係型資料庫。

2.2 路由樹與匹配器機制 (dispatch/ & matcher/)

flowchart TD
    In["接收告警 (LabelSet)"] --> Match{"當前節點 Matchers 匹配?"}
    Match -->|否| Reject["跳過當前分支"]
    Match -->|是| Children{"遍歷子節點 (從左至右 DFS)"}
    Children -->|子節點匹配且 continue=false| StopSiblings["處理該子節點，中斷同層遍歷 (break)"]
    Children -->|子節點匹配且 continue=true| ContSiblings["處理該子節點，繼續比對同層下一個子節點"]
    Children -->|所有子節點皆不匹配| Fallback["由當前節點 (或 Root) 本身處理"]
    StopSiblings --> SlotAssign["分配至對應 slot (去重相同的 Route 規則)"]
    ContSiblings --> SlotAssign
    Fallback --> SlotAssign
Matcher 匹配器底層原理：正則強制自動錨定

位於 pkg/labels/matcher.go，Alertmanager 在編譯正則表達式匹配器時，會強制套用起訖錨點：

re, err := regexp.Compile("^(?:" + v + ")$")

這意味著 service =~ "api" 僅會精確匹配字串 "api"，絕不會模糊命中 "api-gateway"。如需前綴匹配，務必顯式撰寫為 service =~ "api.*"。

缺失標籤 (Absent Labels) 規則：未定義的標籤在比對時視同空字串 ""。因此 env = "" 會命中所有未設置 env 標籤的告警，而 env != "" 則精確過濾出帶有 env 標籤且值不為空的告警。

Route Tree 遍歷演算法特性：

  • 屬性繼承 (RouteOpts Inheritance)：子節點自動繼承父節點的 Receiver、GroupBy、GroupWait、GroupInterval、RepeatInterval。子節點定義的參數原地覆蓋繼承值。
  • continue: true 控制流：預設子路由命中後會中斷同層後續搜尋；若啟用 continue: true，則允許繼續比對同層兄弟節點，這是實作「主告警送至 PagerDuty，同時抄送一份給 Slack 稽核頻道」的核心配置。
  • Fallback 原則：若告警符合當前節點，但子節點均未命中，則當前節點即為匹配節點；若無任何子節點匹配，最後由根節點（Root）承接。
  • 槽位去重優化 (slot)：若多條路由具有相同的 Key 與完全相等的選項（RouteOpts.equal），Dispatcher 會將它們歸納到同一個內部 slot 物件，避免重複建立分組狀態機。

2.3 告警分組 (aggrGroup) 與三大時間參數

Alertmanager 在分組時，會從告警中提取 group_by 所指定的標籤集合，並結合所屬路由 Key，計算出全局唯一的 GroupKey：

GroupKey = RouteKey : GroupByLabelSet

每個獨立的 GroupKey 在記憶體中對應一個獨立運行的狀態機：aggrGroup。

分組計時器運作時序 (Timeline)

  │  (啟動 group_wait 計時器)
  ├─ [t=10s] 告警 B 到達 (同組，靜默聚合存入 store)

參數名稱 建議設定值 內部運作機制與架構目的
group_wait 10s ~ 30s 初次通知緩衝時間。
新群組產生時啟動。在緩衝期內吸收同組相繼觸發的告警，合併為單一通知送出，防範雪崩式告警碎片。
group_interval 5m 群組狀態變更時的發送間隔。
已發出過初次通知後，若有新告警加入該組或既有告警恢復（Resolved），必須等待滿 group_interval 才會發送更新批次，防止高頻抖動。
repeat_interval 4h ~ 12h 告警持續存在時的重新發送週期。
若告警維持 Firing 且標籤集合無任何變化，配合 nflog 去重日誌，僅在間隔超過此時間時重新提醒一次。

2.4 通知處理流水線與去重階段 (notify/ & nflog/)

在 notify/notify.go 中，Alertmanager 將發送流程解耦為裝飾者模式的 Stage 責任鏈流水線： 

flowchart LR
    A["aggrGroup.flush()"] --> B["ClusterGossipSettleStage"]
    B --> C["MuteStage (Inhibitor)"]
    C --> D["TimeActiveStage / TimeMuteStage"]
    D --> E["MuteStage (Silencer)"]
    E --> F["FanoutStage (各 Receiver 管道)"]
    
    subgraph ReceiverPipe["Per-Receiver Pipeline"]
        F1["ClusterWaitStage"] --> F2["DedupStage (nflog 比對)"]
        F2 --> F3["RetryStage (Notifier 發送)"]
        F3 --> F4["SetNotifiesStage (寫入日誌並廣播)"]
    end
    F --> ReceiverPipe
  1. ClusterGossipSettleStage：節點剛加入叢集或重啟時暫緩發送，等待成員狀態完成 Gossip 初始同步。
  2. MuteStage (Inhibitor)：比對 inhibit_rules。若系統中存在符合條件的根因告警（Source Alert），且當前告警（Target Alert）滿足標籤相等性，則直接剔除。
  3. TimeActiveStage / TimeMuteStage：評估 time_intervals（如週末、非辦公時間），決定是否靜默。
  4. MuteStage (Silencer)：檢查使用者建立的 Silence 靜音規則。
  5. FanoutStage：將告警組分派給各目標接收端（Slack、Webhook 等），進入專屬子階段：
    • ClusterWaitStage：依據叢集節點排名等待對應階梯延遲。
    • DedupStage：查詢 NotificationLog (nflog)。若本組告警集合與前次相同且尚未逾期 repeat_interval，則標記 ReasonDoNotNotify 並直接中斷。
    • RetryStage：執行外部網路請求（HTTP POST 到 Slack 等），具備指數退避重試能力。
    • SetNotifiesStage：發送成功後，將本次發送記錄寫入本地 nflog，並立即向 Gossip 網路廣播。

3. Alertmanager 高可用叢集 (HA Cluster) 與去重機制深入剖析

3.1 設計哲學：CAP 定理與「Fail-Open」原則

在分散式系統 CAP 定理中，Alertmanager 選擇了 AP（可用性與分區容忍性）。

其核心設計哲學為「Fail-Open (寧可多發，不可漏發)」： 告警系統首要目標是將基礎設施或業務異常百分之百送達維運人員手中。在面對網路抖動、分區（Split-Brain）或狀態同步衝突時，Alertmanager 寧可向接收端發送重複的通知，也絕不冒著遺漏關鍵告警的風險去追求嚴格的強一致性（CP）。

3.2 通訊底層：HashiCorp Memberlist Gossip 協議

Alertmanager 底層採用了 HashiCorp memberlist 函式庫建立 Full-Mesh 去中心化 Gossip 拓撲：

  • 通訊埠口：預設監聽 9094 TCP/UDP。
    • UDP：負責低延遲的 Ping/Ack 節點存活性心跳探測。
    • TCP：負責可靠的狀態資料全量推送 (Push/Pull) 與狀態廣播 (Broadcast)。
  • 節點狀態生命週期： Alive (存活) → Suspect (可疑，心跳超時) → Dead (判定離線)。

3.3 狀態同步與 CRDT 合併（nflog 與 silences）

在叢集 Gossip 網路中，主要複製兩類狀態資料（以 Protobuf 格式封裝）：

同步狀態 檔案路徑與結構 衝突解決與合併演算法
nflog (Notification Log) data/nflog (nflogpb.Entry) 記錄每個 Receiver + GroupKey 組合的最後發送時間與告警指紋集合。採用 最後寫入者勝 (Last-Write-Wins, LWW)，以最新時間戳記合併。
silences (靜音資料) data/silences (silencepb.Silence) 使用者在任何節點建立的靜音規則。以 UpdatedAt 最新者獲勝。刪除操作本質上是建立一個過期時間為當前的更新（Tombstone）並向外擴散。
為何原始告警本體不進行 Gossip 同步？

Prometheus 每隔一個評估週期（如 15 秒）就會自動將所有 Firing 與 Resolved 告警向 Alertmanager 重新發送。告警本體僅存於各節點本地記憶體，因此完全不需要消耗寶貴的 Gossip 頻寬同步原始告警。

  1. 節點位置排序 (p.Position())： 在 cluster/cluster.go 中，節點取得當前叢集成員列表，並按照節點名稱的字典序進行排序：
    cluster/cluster.go 
    func (p *Peer) Position() int {
    all := p.mlist.Members()
    sort.Slice(all, func(i, j int) bool {
        return all[i].Name < all[j].Name
    })
    for i, m := range all {
        if m.Name == p.Self().Name {
            return i
        }
    }
    return 0
}
  2. 階梯延遲計算 (clusterWait)： 在 app/cluster.go 中，通知管線在執行發送前會先睡眠一段偏置時間：
    WaitDuration = Position × peer_timeout (預設 peer_timeout = 15s)
    • 節點 0（Position 0）：等待 $0 imes 15 ext{s} = 0 ext{s}$（立即處理發送）。
    • 節點 1（Position 1）：等待 $1 imes 15 ext{s} = 15 ext{s}$。
    • 節點 2（Position 2）：等待 $2 imes 15 ext{s} = 30 ext{s}$。
  3. 發送與 Gossip 狀態廣播： 節點 0 最先醒來，查詢 nflog 發現無發送紀錄，隨即發送給 Slack。發送成功後，於 SetNotifiesStage 寫入本地 nflog，並透過 Gossip 廣播給其他節點。 節點 1 在 15 秒後喚醒，查詢 nflog 時發現節點 0 剛廣播過來的發送紀錄，判定該告警已發送過，DedupStage 直接靜默拋棄。
  4. 無縫故障轉移 (Failover)： 若節點 0 宕機或外部連線失敗，便無法寫入與廣播 nflog。當節點 1 在 15 秒後醒來時，發現本地 nflog 依舊沒有這筆發送記錄，節點 1 便會自動接手發送，達成容錯備援。

3.5 狀態沉澱機制 (Gossip Settling)

剛加入叢集或重啟後的 Alertmanager 節點，若立即開始發送通知，會因尚未接收到其他節點廣播的 Silence 或最新的 nflog 去重紀錄，導致誤發或重複發送。

為此，Alertmanager 在流水線開頭加入了 ClusterGossipSettleStage：

  • 節點啟動後會先進入「沉澱觀察期」。
  • 該演算法會定期檢查叢集成員數量，必須等到連續 3 次檢查期間成員數保持穩定（或達到 settle 超時時間）。
  • 沉澱期間：節點正常接收並存儲 Prometheus 推送的告警，但暫緩執行發送流水線，直到全局拓撲與狀態同步完成。

3.6 網路分區與腦裂 (Split-Brain) 處理

當跨機房網路中斷時，Alertmanager 叢集可能會被切分為多個互不連通的孤島：

分區前後架構拓撲
分裂前：
[ AM-1 ] <─── Gossip ───> [ AM-2 ] <─── Gossip ───> [ AM-3 ]

分裂後 (網路分區)：
分區 A: [ AM-1 ] (孤島)      |  分區 B: [ AM-2 ] <───> [ AM-3 ]
  • 分區 A (AM-1)：在自身視角中叢集僅剩 1 台，AM-1 成為 Position 0，等待 0 秒 → 發送告警。
  • 分區 B (AM-2, AM-3)：AM-2 成為分區內的 Position 0，等待 0 秒 → 發送告警；AM-3 為 Position 1，被 AM-2 的 nflog 去重。
  • 結果：維運人員會收到 兩封重複的告警。
  • 網路自癒（Heal）：當網路分區修復後，Memberlist 自動重新建立連線，兩邊的 nflog 與 silences 進行 LWW 合併，後續通知立刻恢復為單份發送。完全體現 Fail-Open 原則。

3.7 持久化儲存與狀態快照 (Snapshot)

每個 Alertmanager 實例均會定期將記憶體狀態快照寫入磁碟：

  • data/nflog：通知歷史日誌快照。
  • data/silences：靜音規則快照。
容器環境警示：務必為 Alertmanager 掛載 PersistentVolumeClaim (PVC)

在 Kubernetes / Rancher 等容器環境中，若使用預設的 EmptyDir，Pod 重啟時本地快照將徹底遺失；若多個 Pod 同時滾動重啟，可能導致剛被 Silence 的告警再次爆發或造成通知重複發送。

3.8 核心黃金法則：Prometheus 嚴禁透過負載均衡器連接

在配置 Prometheus 與 Alertmanager 叢集時，最常見的架構錯誤就是在中間架設 Load Balancer：

  • ❌ 錯誤做法：Prometheus → Load Balancer → Alertmanager Cluster
    破壞了平行獨立評估機制，LB 成為單點故障，且若命中沉澱期實例會引發延遲。
  • ✔️ 正確做法：Prometheus → 直連所有 Alertmanager 實例
    prometheus.yml 
    alerting:
  alertmanagers:
    - static_configs:
        - targets:
            - 'am-1.corp.internal:9093'
            - 'am-2.corp.internal:9093'
            - 'am-3.corp.internal:9093'

4.2 命名空間隔離機制 (Namespace Enforcement)

Rancher Monitoring 的多租戶核心在於 AlertmanagerConfig 的命名空間隔離：

當業務團隊在 app-production 命名空間建立 AlertmanagerConfig 時，Prometheus Operator 在編譯時會強制在該配置的所有路由規則中注入標籤過濾：

Operator 自動注入的 namespace 限制
matchers:
  - name: namespace
    value: app-production
    matchType: "="

資安與穩定性保障：業務團隊無法透過 CRD 截獲其他專案或全集群層級（如 Node、Etcd、Ingress）的告警，實現了真正的專案級告警自治（Self-service）。

5.1 全域 AlertmanagerConfig 範例 (cattle-monitoring-system)

包含 Critical 告警多重分發（PagerDuty + Slack）、Warning 告警分流，以及關鍵的節點宕機抑制規則：

cattle-monitoring-system-alertmanagerconfig.yaml 
apiVersion: monitoring.coreos.com/v1alpha1
kind: AlertmanagerConfig
metadata:
  name: rancher-global-alertmanager-config
  namespace: cattle-monitoring-system
  labels:
    alertmanagerConfig: rancher-monitoring-alertmanager
spec:
  route:
    groupBy: ['alertname', 'cluster', 'namespace', 'service']
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 6h
    receiver: 'slack-default'
    routes:
      # 1. 嚴重級別 (Critical)：直通 PagerDuty，並藉由 continue: true 同時抄送 Slack 緊急頻道
      - matchers:
          - name: severity
            value: critical
        receiver: 'pagerduty-urgent'
        continue: true
      - matchers:
          - name: severity
            value: critical
        receiver: 'slack-sre-critical'

      # 2. 警告級別 (Warning)：發送至監控日常告警頻道
      - matchers:
          - name: severity
            value: warning
        receiver: 'slack-warnings'

      # 3. 節點與硬體基礎設施告警：發送至自動化維運 Webhook
      - matchers:
          - name: alertname
            value: "(KubeNodeNotReady|NodeDiskPressure|NodeMemoryHigh)"
            matchType: "=~"
        receiver: 'infra-ops-webhook'

  inhibitRules:
    # 核心根因抑制：節點離線 (KubeNodeNotReady) 時，自動抑制該節點上的所有衍生 Pod 異常
    - sourceMatch:
        - name: alertname
          value: KubeNodeNotReady
      targetMatch:
        - name: alertname
          value: "(TargetDown|KubePodCrashLooping|KubePodNotReady)"
          matchType: "=~"
      equal: ['node', 'instance']

  receivers:
    - name: 'slack-default'
      slackConfigs:
        - channel: '#alerts-general'
          sendResolved: true
          apiURL:
            name: alert-slack-credentials
            key: webhook-url
          title: '{{ template "slack.default.title" . }}'
          text: '{{ template "slack.default.text" . }}'

    - name: 'slack-sre-critical'
      slackConfigs:
        - channel: '#alerts-sre-critical'
          sendResolved: true
          apiURL:
            name: alert-slack-credentials
            key: webhook-url

    - name: 'slack-warnings'
      slackConfigs:
        - channel: '#alerts-warnings'
          sendResolved: true
          apiURL:
            name: alert-slack-credentials
            key: webhook-url

    - name: 'pagerduty-urgent'
      pagerdutyConfigs:
        - serviceKey:
            name: alert-pagerduty-secret
            key: service-key
          sendResolved: true

    - name: 'infra-ops-webhook'
      webhookConfigs:
        - url: 'https://ops-gateway.corp.internal/v1/alerts'
          sendResolved: true

6. 維運排錯與指標監控 (Operations & Troubleshooting)

6.1 告警重複接收的四大排查點

  1. Gossip 通訊埠 (:9094) 受阻： 每個 Pod 都各自發送出一份相同告警。NetworkPolicy 或防火牆未放行 TCP/UDP 9094 埠，導致去重日誌無法同步。 使用 amtool cluster show 確認叢集所有節點狀態為 ready。
  2. PVC 遺失導致狀態清空： 預設 Rancher 若使用 EmptyDir，Pod 重啟時本機 nflog 與 silences 會丟失。強烈建議在 Alertmanager CR 中設定 StorageSpec 掛載 PVC。
  3. repeat_interval 設定過短： 若設為 5 分鐘，會使正常週期提醒被誤判為重複發送。
  4. 跨路由 group_by 標籤維度不一致： 不同路由若定義不同的分組維度，會計算出不同的 GroupKey，並在獨立的 aggrGroup 中各自觸發通知。

6.2 熱重載與診斷工具流

維運排錯診斷指令集 (Bash) 
# 1. 檢查 config-reloader sidecar 容器日誌
kubectl logs -n cattle-monitoring-system alertmanager-rancher-monitoring-alertmanager-0 -c config-reloader -f

# 2. 檢驗目前載入的最終設定檔
kubectl exec -it -n cattle-monitoring-system alertmanager-rancher-monitoring-alertmanager-0 -c alertmanager --   amtool config show --alertmanager.url=http://localhost:9093

# 3. 測試路由比對 (驗證特定標籤會走向哪一個 Receiver)
kubectl exec -it -n cattle-monitoring-system alertmanager-rancher-monitoring-alertmanager-0 -c alertmanager --   amtool config routes test --alertmanager.url=http://localhost:9093 severity=critical alertname=KubeNodeNotReady

# 4. 檢查叢集 Gossip 成員健康狀態
kubectl exec -it -n cattle-monitoring-system alertmanager-rancher-monitoring-alertmanager-0 -c alertmanager --   amtool cluster show --alertmanager.url=http://localhost:9093

6.3 關鍵監控指標 (Prometheus Metrics)

指標名稱 正常預期 異常代表意義與因應對策
alertmanager_cluster_members 等於副本數 (如 3) 節點發生分區（Split-Brain）或網路失聯，應檢查 9094 埠。
alertmanager_cluster_failed_peers 0 存在失效對等節點，Gossip 同步受阻。
alertmanager_peer_position 0 ~ (Replicas-1) 當前節點在叢集排序中的位置，決定階梯延遲長度。
alertmanager_notifications_failed_total 0 或極低且不持續增加 外部接收端（Slack/PagerDuty/Webhook）網路中斷或 API Token 失效。
alertmanager_alerts_received_total 穩定趨勢 數值陡增代表下游集群發生大範圍告警風暴。
alertmanager_silences{status="active"} 符合維護計畫 活躍靜音數量過多時，應審核是否有忘記清理的永久靜音。
